# NILO Backend — Especificación de API (Auth, Pacientes, Nodos)

Documento de referencia para el desarrollo del frontend. Describe autenticación
(con manejo de refresh token) y los endpoints CRUD de **pacientes** y **nodos**.

---

## 1. Información general

- **Base URL**: `http://localhost:8001/api/v1`
  - En desarrollo local con Docker, la API se publica en el puerto **8001**.
  - Ajusta el host/puerto según el entorno de despliegue.
- **Formato**: JSON en peticiones y respuestas, **excepto el login** (que usa
  `application/x-www-form-urlencoded`, ver abajo).
- **Autenticación**: JWT Bearer. Salvo el login y el refresh, **todos** los
  endpoints requieren la cabecera:
  ```
  Authorization: Bearer <access_token>
  ```
- **Documentación interactiva** (Swagger UI): `http://localhost:8001/docs`

### Roles de usuario

| Rol | Valor |
|-----|-------|
| Administrador | `root` |
| Clínico | `clinician` |
| Paciente | `patient` |

"Staff" = `root` + `clinician`. Los endpoints de gestión (crear/editar/borrar
pacientes y nodos) requieren staff.

## 2. Autenticación

### 2.1. Login

Obtiene el par de tokens (access + refresh).

- **Método / Ruta**: `POST /auth/login`
- **Auth**: no requiere
- **Content-Type**: `application/x-www-form-urlencoded` (¡NO JSON!)
- **Campos del formulario**:
  - `username`: el **email** del usuario (el campo se llama `username` por el
    estándar OAuth2, pero va el email).
  - `password`: la contraseña.

**Ejemplo (curl):**
```bash
curl -X POST http://localhost:8001/api/v1/auth/login \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "username=root@niloapp.com&password=changeme"
```

**Respuesta `200 OK`:**
```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "refresh_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "bearer"
}
```

**Errores:**
- `401 Unauthorized` — email o contraseña incorrectos.
- `403 Forbidden` — usuario inactivo.

> Nota para `fetch`/axios: NO envíes JSON aquí. Usa `URLSearchParams` o
> `FormData`. Ejemplo con `fetch`:
> ```js
> const body = new URLSearchParams({ username: email, password });
> const res = await fetch(`${BASE_URL}/auth/login`, { method: "POST", body });
> ```

### 2.2. Ciclo de vida de los tokens

- **access_token**: corta duración (**60 minutos**). Se envía en cada petición.
- **refresh_token**: larga duración (**30 días**). Solo sirve para obtener un
  nuevo access token. Cada refresh **rota** también el refresh token.

### 2.3. Cómo guardar los tokens (recomendación frontend)

- **access_token**: guárdalo en **memoria** (variable/estado de la app, p. ej.
  un store de Pinia/Redux/Zustand). Es efímero.
- **refresh_token**: guárdalo en almacenamiento persistente para "mantener la
  sesión":
  - **Web**: idealmente una cookie `HttpOnly` + `Secure` (requiere soporte del
    backend; hoy se devuelve en el body, así que la alternativa práctica es
    `localStorage`). Si usas `localStorage`, asume el riesgo de XSS y protege la
    app en consecuencia.
  - **Móvil/desktop**: almacenamiento seguro del sistema (Keychain, Keystore,
    SecureStore, etc.).
- **Nunca** guardes contraseñas. Solo tokens.

### 2.4. Refrescar el access token

- **Método / Ruta**: `POST /auth/refresh`
- **Auth**: no requiere cabecera (el refresh token va en el body)
- **Content-Type**: `application/json`
- **Body**:
```json
{ "refresh_token": "eyJhbGciOi..." }
```

**Ejemplo (curl):**
```bash
curl -X POST http://localhost:8001/api/v1/auth/refresh \
  -H "Content-Type: application/json" \
  -d '{"refresh_token":"eyJhbGciOi..."}'
```

**Respuesta `200 OK`** (nuevo par; guarda **ambos** y descarta los anteriores):
```json
{
  "access_token": "eyJ...nuevo...",
  "refresh_token": "eyJ...nuevo...",
  "token_type": "bearer"
}
```

**Errores:**
- `401 Unauthorized` — refresh token inválido o expirado → forzar logout y
  redirigir al login.

### 2.5. Estrategia de uso recomendada (interceptor)

1. Al hacer login, guarda `access_token` (memoria) y `refresh_token`
   (almacenamiento seguro).
2. Añade `Authorization: Bearer <access_token>` a cada petición.
3. Si una petición devuelve **`401`**:
   - Llama a `POST /auth/refresh` con el `refresh_token`.
   - Si responde `200`: actualiza ambos tokens y **reintenta** la petición
     original.
   - Si responde `401`: borra los tokens y manda al usuario al login.
4. Opcional: refresca de forma proactiva ~1 min antes de que caduque el access
   (a los ~59 min) para evitar el 401.

> Mientras uses el refresh dentro de la ventana de 30 días, la sesión se
> mantiene indefinidamente (el refresh se renueva en cada uso).

### 2.6. Datos del usuario actual

- **Método / Ruta**: `GET /auth/me`
- **Auth**: Bearer
- **Respuesta `200 OK`**: objeto del usuario autenticado (ver `UserOut`).

```bash
curl http://localhost:8001/api/v1/auth/me \
  -H "Authorization: Bearer <access_token>"
```

## 3. Pacientes

Entidad clínica (colección `patients`). Los datos sensibles se almacenan
cifrados en el servidor; la API los devuelve en claro.

- **Lectura** (listar / obtener): cualquier usuario autenticado.
- **Escritura** (crear / editar / borrar): **staff** (`clinician` o `root`).

### 3.1. Modelo de datos

**Enumeraciones:**
- `sex`: `male` | `female` | `other` | `unknown`
- `patient_type`: `adult` | `child` | `neonate` | `other`

**Objeto de paciente (respuesta, `PatientOut`):**
```json
{
  "id": "6a4bca11d59665843e63485a",
  "full_name": "Juan Pérez",
  "medical_record_number": "MRN-00123",
  "birth_date": "1980-05-17",
  "sex": "male",
  "patient_type": "adult",
  "room": "204",
  "bed": "B",
  "is_active": true,
  "notes": "Observaciones...",
  "created_at": "2026-07-07T13:00:00Z"
}
```

### 3.2. Listar pacientes

- **Método / Ruta**: `GET /patients`
- **Auth**: Bearer (cualquier usuario)
- **Query params** (opcionales):
  - `skip` (int, def. `0`) — paginación (offset).
  - `limit` (int, def. `100`) — máximo de resultados.
  - `active_only` (bool, def. `true`) — si `true`, solo pacientes activos.
- **Respuesta `200 OK`**: array de `PatientOut`.

```bash
curl "http://localhost:8001/api/v1/patients?skip=0&limit=50&active_only=true" \
  -H "Authorization: Bearer <access_token>"
```

### 3.3. Obtener un paciente

- **Método / Ruta**: `GET /patients/{patient_id}`
- **Auth**: Bearer
- **Respuesta `200 OK`**: `PatientOut`.
- **Errores**: `404` si no existe.

### 3.4. Añadir paciente

- **Método / Ruta**: `POST /patients`
- **Auth**: Bearer **staff**
- **Content-Type**: `application/json`
- **Body (`PatientCreate`):**

| Campo | Tipo | Obligatorio | Notas |
|-------|------|:-----------:|-------|
| `full_name` | string | **Sí** | |
| `medical_record_number` | string | No | Único si se envía |
| `birth_date` | string (YYYY-MM-DD) | No | |
| `sex` | enum | No | def. `unknown` |
| `patient_type` | enum | No | def. `adult` |
| `room` | string | No | |
| `bed` | string | No | |
| `notes` | string | No | |

```bash
curl -X POST http://localhost:8001/api/v1/patients \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{
    "full_name": "Juan Pérez",
    "medical_record_number": "MRN-00123",
    "birth_date": "1980-05-17",
    "sex": "male",
    "patient_type": "adult",
    "room": "204",
    "bed": "B",
    "notes": "Ingreso por..."
  }'
```

- **Respuesta `201 Created`**: `PatientOut`.
- **Errores**: `409 Conflict` si el `medical_record_number` ya existe;
  `403` si no eres staff.

### 3.5. Modificar paciente

- **Método / Ruta**: `PATCH /patients/{patient_id}`
- **Auth**: Bearer **staff**
- **Content-Type**: `application/json`
- **Body (`PatientUpdate`)**: parcial — envía **solo** los campos a cambiar.
  Campos disponibles: `full_name`, `medical_record_number`, `birth_date`,
  `sex`, `patient_type`, `room`, `bed`, `is_active`, `notes`.

```bash
curl -X PATCH http://localhost:8001/api/v1/patients/6a4bca11d59665843e63485a \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{ "room": "301", "is_active": false }'
```

- **Respuesta `200 OK`**: `PatientOut` actualizado.
- **Errores**: `404` si no existe; `403` si no eres staff.

### 3.6. Eliminar paciente

- **Método / Ruta**: `DELETE /patients/{patient_id}`
- **Auth**: Bearer **staff**
- **Respuesta `204 No Content`** (sin body).
- **Errores**: `404` si no existe; `403` si no eres staff.

```bash
curl -X DELETE http://localhost:8001/api/v1/patients/6a4bca11d59665843e63485a \
  -H "Authorization: Bearer <access_token>"
```

## 4. Nodos

Un **nodo** es un dispositivo físico al que se conectan los dispositivos de
monitorización. `access_password` se guarda cifrada en el servidor y se
devuelve en claro en la API.

- **Lectura** (listar / obtener): cualquier usuario autenticado.
- **Escritura** (crear / editar / borrar): **staff** (`clinician` o `root`).

### 4.1. Modelo de datos

**Objeto de nodo (respuesta, `NodeOut`):**
```json
{
  "id": "6a4bca11d59665843e63485b",
  "name": "Nodo UCI Sala 1",
  "mac_address": "AA:BB:CC:DD:EE:FF",
  "public_ip": "203.0.113.10",
  "ddns": "nodo1.ddns.net",
  "bluetooth_enabled": true,
  "wifi_enabled": true,
  "wired_enabled": false,
  "address": "C/ Falsa 123",
  "zip": "28001",
  "city": "Madrid",
  "location": "UCI - Box 3",
  "latitude": 40.4168,
  "longitude": -3.7038,
  "access_password": "secreto-del-dispositivo",
  "last_update": "2026-07-07T13:30:00Z",
  "last_update_ddns": "2026-07-07T12:00:00Z",
  "created_at": "2026-07-01T10:00:00Z",
  "updated_at": "2026-07-07T13:30:00Z"
}
```

**Campos:**

| Campo | Tipo | Notas |
|-------|------|-------|
| `id` | string | Generado por el servidor (solo lectura) |
| `name` | string | Obligatorio al crear |
| `mac_address` | string | Obligatorio al crear. **Único** |
| `public_ip` | string \| null | |
| `ddns` | string \| null | |
| `bluetooth_enabled` | bool | def. `false` |
| `wifi_enabled` | bool | def. `false` |
| `wired_enabled` | bool | conexión por cable, def. `false` |
| `address` | string \| null | |
| `zip` | string \| null | Código postal |
| `city` | string \| null | |
| `location` | string \| null | Ubicación descriptiva |
| `latitude` | number \| null | |
| `longitude` | number \| null | |
| `access_password` | string \| null | Credencial de acceso al dispositivo |
| `last_update` | datetime \| null | ISO 8601 |
| `last_update_ddns` | datetime \| null | ISO 8601 |
| `created_at` / `updated_at` | datetime | Solo lectura |

### 4.2. Listar nodos

- **Método / Ruta**: `GET /nodes`
- **Auth**: Bearer (cualquier usuario)
- **Query params** (opcionales): `skip` (def. `0`), `limit` (def. `100`).
- **Respuesta `200 OK`**: array de `NodeOut`.

```bash
curl "http://localhost:8001/api/v1/nodes?skip=0&limit=100" \
  -H "Authorization: Bearer <access_token>"
```

### 4.3. Obtener un nodo

- **Método / Ruta**: `GET /nodes/{node_id}`
- **Auth**: Bearer
- **Respuesta `200 OK`**: `NodeOut`.
- **Errores**: `404` si no existe.

### 4.4. Añadir nodo

- **Método / Ruta**: `POST /nodes`
- **Auth**: Bearer **staff**
- **Content-Type**: `application/json`
- **Body (`NodeCreate`)**: obligatorios `name` y `mac_address`; el resto
  opcional (ver tabla de campos).

```bash
curl -X POST http://localhost:8001/api/v1/nodes \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Nodo UCI Sala 1",
    "mac_address": "AA:BB:CC:DD:EE:FF",
    "public_ip": "203.0.113.10",
    "ddns": "nodo1.ddns.net",
    "bluetooth_enabled": true,
    "wifi_enabled": true,
    "wired_enabled": false,
    "address": "C/ Falsa 123",
    "zip": "28001",
    "city": "Madrid",
    "location": "UCI - Box 3",
    "latitude": 40.4168,
    "longitude": -3.7038,
    "access_password": "secreto-del-dispositivo"
  }'
```

- **Respuesta `201 Created`**: `NodeOut`.
- **Errores**: `409 Conflict` si la `mac_address` ya existe; `403` si no eres
  staff.

### 4.5. Actualizar nodo

- **Método / Ruta**: `PATCH /nodes/{node_id}`
- **Auth**: Bearer **staff**
- **Content-Type**: `application/json`
- **Body (`NodeUpdate`)**: parcial — envía **solo** los campos a cambiar.
  Todos los campos del nodo son actualizables (excepto `id`, `created_at`,
  `updated_at`).

```bash
curl -X PATCH http://localhost:8001/api/v1/nodes/6a4bca11d59665843e63485b \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{ "wifi_enabled": false, "public_ip": "203.0.113.20" }'
```

- **Respuesta `200 OK`**: `NodeOut` actualizado.
- **Errores**: `404` si no existe; `409` si la nueva `mac_address` ya existe en
  otro nodo; `403` si no eres staff.

### 4.6. Eliminar nodo

- **Método / Ruta**: `DELETE /nodes/{node_id}`
- **Auth**: Bearer **staff**
- **Respuesta `204 No Content`** (sin body).
- **Errores**: `404` si no existe; `403` si no eres staff.

```bash
curl -X DELETE http://localhost:8001/api/v1/nodes/6a4bca11d59665843e63485b \
  -H "Authorization: Bearer <access_token>"
```

## 5. Resumen de endpoints

| Método | Ruta | Auth | Descripción |
|--------|------|------|-------------|
| POST | `/auth/login` | — | Login (form-urlencoded) → access + refresh |
| POST | `/auth/refresh` | — | Renovar tokens (JSON con refresh_token) |
| GET | `/auth/me` | Bearer | Usuario actual |
| GET | `/patients` | Bearer | Listar pacientes |
| GET | `/patients/{id}` | Bearer | Obtener paciente |
| POST | `/patients` | Staff | Crear paciente |
| PATCH | `/patients/{id}` | Staff | Modificar paciente |
| DELETE | `/patients/{id}` | Staff | Eliminar paciente |
| GET | `/nodes` | Bearer | Listar nodos |
| GET | `/nodes/{id}` | Bearer | Obtener nodo |
| POST | `/nodes` | Staff | Crear nodo |
| PATCH | `/nodes/{id}` | Staff | Actualizar nodo |
| DELETE | `/nodes/{id}` | Staff | Eliminar nodo |

## 6. Códigos de estado comunes

| Código | Significado |
|--------|-------------|
| `200` | OK |
| `201` | Creado |
| `204` | OK sin contenido (deletes) |
| `401` | No autenticado / token inválido o expirado → refrescar o login |
| `403` | Autenticado pero sin permisos (no eres staff) |
| `404` | Recurso no encontrado |
| `409` | Conflicto (MAC o nº historia clínica duplicado) |
| `422` | Body/campos inválidos (revisa formato; el login debe ser form-urlencoded) |
