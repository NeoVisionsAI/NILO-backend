# Handoff frontend: un solo session id (Mongo = MinIO)

## Problema que veías

- UI mostraba un **UUID** (`external_session_id`).
- MinIO usaba **`6b05b8423b658695fd416fba`** (`MonitoringSession.id`).

No era “dos sesiones distintas” en MinIO: había **dos creaciones de sesión** en el flujo antiguo del front:

1. `POST /sessions` + `crypto.randomUUID()` → sesión A (la que mostraba la UI al copiar UUID).
2. `PATCH` con `monitoring_active: true` → el backend llamaba `start_patient_monitoring` y creaba sesión B (la que queda en `active_session_id` y en MinIO).

## Backend (ya hecho)

- `POST /users/{id}/monitoring/start`: una sola sesión; `external_session_id = str(session.id)` tras el insert.
- `POST /sessions` sin `external_session_id`: mismo default.
- Ingestión y rutas MinIO siguen usando `session_id` = **ObjectId**.

## Qué debe hacer el frontend

### 1. Dejar de crear sesión a mano al activar monitorización

**No** usar: `POST /sessions` + UUID + `PATCH monitoring_active`.

**Sí** usar:

```http
POST /api/v1/users/{user_id}/monitoring/start
→ { user, session }
```

```http
POST /api/v1/users/{user_id}/monitoring/stop
→ user
```

(O solo `PATCH` con cambio de `monitoring_active`; el backend ya delega en lifecycle, pero entonces no recibes `session` en la respuesta — preferible `monitoring/start`.)

### 2. Mostrar siempre `session.id`

En `ActiveSessionInfo.tsx` (y copia al portapapeles):

- Antes: `technicalId = session.external_session_id ?? session.id`
- Ahora: **`session.id`** (etiqueta: “Id de sesión (MinIO)”).

### 3. Subidas

Seguir usando `patient_profile.active_session_id` o `session.id` del `monitoring/start` — **nunca** un UUID generado en el navegador.

## Sesiones ya abiertas con UUID antiguo

Seguirán con `external_session_id` distinto hasta que cierres y vuelvas a activar monitorización (nueva sesión alinea `external_session_id` con `id`). Los datos en MinIO de la sesión activa siguen bajo el ObjectId correcto en `active_session_id`.
