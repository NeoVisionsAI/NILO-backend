# Servicio systemd (arranque automático y recuperación)

Para la **VM del backend** (Mongo/MinIO en el host u otro sitio): el servicio arranca la API al **boot** y, si algo falla, **reintenta** tras unos segundos.

## Modos

| Modo | Comando install | Qué levanta |
|------|-----------------|-------------|
| **VM (recomendado)** | `sudo ./scripts/install-systemd-service.sh` | `docker-compose.api-only.yml` |
| Stack completo | `sudo ./scripts/install-systemd-service.sh --full` | `docker-compose.yml` (mongo + minio + api) |
| Sin Docker | `sudo ./scripts/install-systemd-service.sh --native` | `uvicorn` desde `.venv` |

## Instalación rápida (VM + Docker)

Tras un **`./deploy.sh`** en el host o VM con stack completo, el script instala y habilita **`nilo-backend.service`** (pide `sudo` si hace falta). También intenta `systemctl enable docker`.

Para desactivar solo esa parte: `NILO_SYSTEMD=0 ./deploy.sh` o `./deploy.sh --no-systemd`.

1. En el **host**: Mongo y MinIO (incluidos en `./deploy.sh`, o solo `docker compose up -d mongo minio`).
2. En la **VM**: `config.yaml` con `NILO_INFRA_HOST` = IP del host.
3. `credentials.env` presente en el repo.
4. Usuario de servicio en el grupo `docker`:

```bash
sudo usermod -aG docker "$USER"
# cerrar sesión y volver a entrar, o: newgrp docker
```

5. Instalar y arrancar:

```bash
cd /ruta/a/NILO-backend
sudo ./scripts/install-systemd-service.sh
```

## Recuperación ante fallos

### Docker (api-only o full)

- **systemd**: si `docker compose up` falla al arrancar (Docker no listo, etc.), reintenta cada **15 s** (`Restart=on-failure`).
- **Contenedor**: en compose, `restart: always` — si el proceso uvicorn dentro del contenedor muere, Docker lo vuelve a levantar.
- **Healthcheck**: el contenedor API se comprueba con `GET /health`; tras varios fallos Docker reinicia el contenedor.

### Nativo (uvicorn)

- **systemd** `Restart=on-failure` + `RestartSec=5` — reinicio a los **5 segundos** tras caída.
- Límite: 10 reinicios en 5 minutos (`StartLimitBurst`); luego hay que revisar logs.

## Comandos útiles

```bash
sudo systemctl status nilo-backend
sudo journalctl -u nilo-backend -f
sudo systemctl restart nilo-backend      # tras cambiar código (Docker: rebuild manual o reload)
sudo systemctl stop nilo-backend
sudo ./scripts/install-systemd-service.sh --uninstall
```

Tras actualizar la imagen/código en modo Docker:

```bash
cd /ruta/a/NILO-backend
docker compose -f docker-compose.api-only.yml --env-file credentials.env up -d --build
# o:
sudo systemctl reload nilo-backend
```

## Orden de arranque en la VM

El host ya levanta la VM al reiniciar. En la VM:

1. `docker.service` (si usas Docker).
2. Red disponible (`network-online.target`).
3. `nilo-backend.service` → `docker compose up -d` o uvicorn.

Asegúrate de que Mongo/MinIO en el **host** también arrancan solos (p. ej. otro servicio systemd o `restart: unless-stopped` en el host). Si la API arranca antes de que Mongo responda, el contenedor puede fallar el healthcheck y reiniciarse hasta que el host esté listo — comportamiento esperado.

## Personalización

- Otro usuario: `sudo ./scripts/install-systemd-service.sh --user miuser`
- Puerto nativo: `API_PORT=8001 sudo ./scripts/install-systemd-service.sh --native`
- Unidad generada: `/etc/systemd/system/nilo-backend.service` (plantillas en `deploy/systemd/`)
