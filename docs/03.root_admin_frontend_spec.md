# NILO Root Admin - Especificacion frontend

Vista exclusiva cuando el usuario logueado tiene type_user = "root".
Base URL API: http://192.168.1.43:8001/api/v1  (ajustar segun entorno)

Tras login, comprobar con GET /auth/me que type_user es "root".
Si no es root, redirigir al dashboard de clinico/paciente habitual.

Todos los endpoints de esta spec exigen:
  Authorization: Bearer <access_token>
  y rol root (403 si no).


================================================================================
ESTRUCTURA DE LA VISTA ROOT
================================================================================

Menu principal sugerido:

  1. Pacientes
  2. Medicos (clinicos)
  3. NILO Nodes
  4. (opcional) enlace a Swagger / health

Cada seccion: listado con busqueda + alta + edicion + borrado.


================================================================================
CREDENCIALES DEMO
================================================================================

  email: root@niloai.net
  password: root

Login igual que el resto de roles:
  POST /api/v1/auth/login
  Content-Type: application/x-www-form-urlencoded
  username=root@niloai.net&password=root


================================================================================
1. PACIENTES (admin)
================================================================================

Prefijo: /api/v1/admin/patients

Listar y buscar:
  GET /admin/patients

  Query params (todos opcionales, combinable):
    q           texto libre (nombre, apellidos, email, direccion, pais, habitacion...)
    name        filtro parcial nombre
    lastname    filtro parcial apellidos
    email       filtro parcial email
    country     filtro parcial pais
    zip         filtro parcial codigo postal
    skip        paginacion (default 0)
    limit       paginacion (default 100, max 500)

  Respuesta: array de UserOut (type_user = patient)

Detalle:
  GET /admin/patients/{user_id}

Crear:
  POST /admin/patients
  Content-Type: application/json

  Body (AdminPatientCreate):
  {
    "name": "Pablo",
    "lastname": "Garcia",
    "email": "pablo@example.com",
    "password": "changeme",
    "birthdate": "1980-05-01",
    "address": "Calle Mayor 1",
    "zip": "28001",
    "country": "Espana",
    "phone": "+34600000001",
    "is_active": true,
    "patient_profile": {
      "type_patient": "adult",
      "monitoring_active": true,
      "medical_record_number": "MRN-001",
      "sex": "male",
      "room": "101",
      "bed": "A",
      "notes": "",
      "relative_name": "Maria Garcia",
      "relative_contact": "+34600000002",
      "relative_address": "..."
    }
  }

  Al crear se sincroniza automaticamente el Patient clinico interno.

Modificar:
  PATCH /admin/patients/{user_id}
  Mismo esquema que UserUpdate (campos opcionales, incluye patient_profile, is_active, password)

Eliminar:
  DELETE /admin/patients/{user_id}
  Respuesta: 204 (borra tambien el Patient clinico vinculado)

================================================================================
3. NILO NODES (admin)
================================================================================

Prefijo: /api/v1/admin/nodes

Listar y buscar:
  GET /admin/nodes

  Query params:
    q           texto libre (nombre, MAC, IPs, DDNS, ciudad, direccion...)
    name        filtro parcial nombre
    mac_address filtro parcial MAC
    city        filtro parcial ciudad
    public_ip   filtro parcial IP publica
    ddns        filtro parcial hostname DDNS
    skip, limit

Detalle:
  GET /admin/nodes/{node_id}

Crear:
  POST /admin/nodes

  Body:
  {
    "name": "Node UCI-1",
    "mac_address": "AA:BB:CC:DD:EE:FF",
    "access_password": "node-secret",
    "address": "Planta 2",
    "city": "Madrid",
    "zip": "28001",
    "location": "UCI box 3",
    "bluetooth_enabled": false,
    "wifi_enabled": true,
    "wired_enabled": true,
    "ssh_enabled": false
  }

  mac_address es unico. access_password se guarda cifrado; el node la usa en heartbeat.

Modificar:
  PATCH /admin/nodes/{node_id}
  NodeUpdate (todos los campos opcionales)

Eliminar:
  DELETE /admin/nodes/{node_id}


================================================================================
TELEMETRIA EN LISTADO DE NODOS (campos utiles en UI)
================================================================================

NodeOut incluye ademas de la config estatica:

  private_ip       ultima IP privada reportada
  public_ip        ultima IP publica (estilo DDNS)
  ddns             hostname si lo envia el node
  uptime_seconds   tiempo operativo en segundos
  ssh_enabled      si SSH esta activo en el node
  telemetry        dict abierto con metricas extra (versiones, CPU, etc.)
  last_heartbeat   ultima vez que el node llamo a heartbeat
  last_update_ddns  ultima vez que cambio IP publica o DDNS

Mostrar en la tabla:
  - nombre, MAC, IP publica, last_heartbeat (hace cuanto), ssh_enabled, monitoring link


================================================================================
HEARTBEAT DEL NODE (lo llama nilo-node, NO el frontend root)
================================================================================

  POST /api/v1/nodes/heartbeat
  Content-Type: application/json
  SIN Authorization Bearer (autentica con MAC + password)

  Body:
  {
    "mac_address": "AA:BB:CC:DD:EE:FF",
    "access_password": "node-secret",
    "private_ip": "192.168.1.50",
    "public_ip": "203.0.113.10",
    "ddns": "nilo-node-1.example.com",
    "uptime_seconds": 86400.5,
    "ssh_enabled": true,
    "wifi_enabled": true,
    "wired_enabled": false,
    "telemetry": {
      "software_version": "1.0.0",
      "cpu_percent": 12.5
    }
  }

  El backend mergea telemetry en el dict existente.
  Actualiza last_heartbeat y last_update_ddns si cambia public_ip o ddns.

  nilo-node deberia llamar esto cada X segundos (ej. 30-60s).


================================================================================
BUSQUEDA: NOTAS PARA EL FRONTEND
================================================================================

- Parametro "q" busca en texto libre (util para un unico campo de busqueda en UI).
- Filtros name/lastname/email/country/zip son opcionales y combinables.
- Los datos personales estan cifrados en BD; la busqueda parcial se resuelve en
  servidor cargando y filtrando (OK para volumenes admin actuales).
- country exacto sin otros filtros puede ser mas rapido en servidor.


================================================================================
FLUJO UI RECOMENDADO
================================================================================

1. Login root
2. GET /auth/me -> verificar type_user === "root"
3. Layout con tabs: Pacientes | Medicos | Nodes
4. Cada tab:
   - barra busqueda (param q) + filtros avanzados opcionales
   - tabla paginada (skip/limit)
   - boton Nuevo -> modal formulario POST
   - fila -> Ver/Editar PATCH -> Eliminar DELETE con confirmacion
5. Tab Nodes: columna "Ultimo heartbeat" en rojo si hace > 2 min sin heartbeat


================================================================================
ERRORES
================================================================================

  401 - token expirado -> refresh o re-login
  403 - no es root
  404 - recurso no encontrado
  409 - email duplicado, MAC duplicada, MRN duplicado

  POST   /auth/login
  GET    /auth/me


================================================================================
DIFERENCIA CON ENDPOINTS DE CLINICO
================================================================================

El clinico sigue usando /users para pacientes (solo los suyos).
El root debe usar /admin/* para gestion global y busqueda.

Los endpoints /users, /nodes (sin /admin) siguen existiendo para el flujo
clinico; la vista root puede ignorarlos y usar solo /admin.
