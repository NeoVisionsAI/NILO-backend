# Sesiones de monitorización (`MonitoringSession`)

Este documento describe el modelo de datos y la API de **sesiones de monitorización** en NILO. Sustituye el concepto anterior de `Recording`, que mezclaba “sesión clínica” con “solo vídeo”.

## Motivación

Un paciente puede estar monitorizado durante **minutos, horas o días**. En ese intervalo:

- El **vídeo** llega en trozos (`VideoSegment`) con ventanas temporales propias; no cubre necesariamente toda la sesión.
- **Audio**, **vitales**, **landmarks** y **eventos de dolor** también son **parciales** y pueden solaparse o dejar huecos.

Hace falta un contenedor común que agrupe todo lo capturado en un periodo clínico. Ese contenedor es **`MonitoringSession`**.

## Modelo de datos (MongoDB / Beanie)

| Colección | Documento | Rol |
|-----------|-----------|-----|
| `monitoring_sessions` | `MonitoringSession` | Contenedor temporal por paciente |
| `video_segments` | `VideoSegment` | Chunk de vídeo (MinIO + metadatos) |
| `audio_recordings` | `AudioRecording` | Clip de audio |
| `physiological_readings` | `PhysiologicalReading` | Lectura de vitales |
| `body_landmarks` | `BodyLandmarks` | Lote de keypoints |
| `pain_events` | `PainEvent` | Clip de dolor |

### `MonitoringSession`

Campos principales:

- `patient_id` — paciente clínico (`/patients`).
- `node_id` — opcional; ObjectId del nodo NILO (`/nodes`) cuando nilo-node lo envía.
- `external_session_id` — opcional; UUID u otro id del cliente (nilo-node) para correlación.
- `started_at`, `ended_at`, `status` — `active` | `completed` | `cancelled` (enum `MonitoringSessionStatus`).
- `archive_chunk_seconds`, `hls_segment_seconds` — defaults del pipeline de vídeo para esa sesión.

### Modalidades con `session_id` y `node_id` opcional

Todo dato de ingestión **debe** incluir `session_id` y `patient_id` (coherente con la sesión). **`node_id` es opcional**: si viene, se guarda en el documento; si no, el resto del payload se persiste igual.

Cuando se envían `node_id` en la ingestión y en la sesión, deben coincidir. Si se envía un `node_id`, el nodo debe existir en `/nodes`.

Al crear sesión, si se envía `node_id` y el paciente tiene nodo asignado, deben coincidir.

### Objetos en MinIO

Las claves de objeto incluyen un subpath con el id de sesión cuando aplica (vídeo, audio, landmarks, dolor), para aislar binarios por sesión bajo el paciente.

## API REST (`/api/v1/sessions`)

| Método | Ruta | Descripción |
|--------|------|-------------|
| POST | `/sessions` | Crear sesión (staff) |
| GET | `/sessions` | Listar (`?patient_id=`, `?node_id=`, `?status_filter=`) |
| GET | `/sessions/{session_id}` | Detalle |
| GET | `/sessions/{session_id}/overview` | Conteos por modalidad |
| POST | `/sessions/{session_id}/end` | Cerrar sesión (`completed`) |
| POST | `/sessions/{session_id}/video-segments` | Pedir presigned PUT de un segmento |
| GET | `/sessions/{session_id}/video-segments` | Listar segmentos |
| POST | `/sessions/video-segments/{segment_id}/confirm` | Confirmar subida |
| GET | `/sessions/video-segments/{segment_id}/download` | Presigned GET |

Cuerpo de creación (ejemplo):

```json
{
  "patient_id": "675abc...",
  "node_id": "675node...",
  "external_session_id": "nilo-node-uuid-1234",
  "archive_chunk_seconds": 300,
  "hls_segment_seconds": 6
}
```

Respuesta de overview:

```json
{
  "session": { "...": "MonitoringSessionOut" },
  "video_segments": 12,
  "audio_clips": 3,
  "physiological_readings": 5400,
  "landmarks_batches": 12,
  "pain_events": 0
}
```

## Flujo recomendado (nilo-node)

1. Login como clinician.
2. Resolver `patient_id` con `GET /patients?node_id=...`.
3. `POST /sessions` con `patient_id` y, recomendado, `node_id` (= `NILO_NODE_ID`) y opcional `external_session_id`.
4. Guardar `session.id` como **`session_id`**. En cada ingestión, enviar **`node_id`** cuando el cliente lo tenga (no es obligatorio).
5. Bucle de captura (vídeo, vitales, audio, …).
6. `POST /sessions/{session_id}/end`.

Detalle de payloads: **`docs/02.nilo_node_ingestion_spec.md`**.

## Migración desde `Recording` / `/recordings`

Cambio **rompedor** en API y esquema:

| Antes | Ahora |
|-------|--------|
| `POST /recordings` | `POST /sessions` |
| `recording_id` | `session_id` |
| `device_id` al crear | `external_session_id` |
| Colección `recordings` | `monitoring_sessions` |
| `VideoSegment.recording_id` | `VideoSegment.session_id` |

**No hay migración automática** de datos legacy en este repositorio.

Entornos de desarrollo sin datos importantes:

```bash
./deploy.sh --down -v   # elimina volúmenes Mongo/MinIO
./deploy.sh
```

Entornos con datos históricos: hace falta un script ETL que:

1. Copie cada `recordings` → `monitoring_sessions` (mapear `device_id` → `external_session_id`).
2. Actualice `video_segments.recording_id` → `session_id`.
3. Rellene `session_id` en otras colecciones si existían sin sesión (o asigne sesiones sintéticas por ventana temporal).
